기준일 2026-11-02 · 적용 시점: [개발 중단점 p1](checkpoint-p1.md) 이후 · 상태: **승인(2026-11-02, 결정 SF-1~SF-8 권고안 채택)** · 2026-11-06 PMS 묶음 AP1·AP2 추가(결정 SF-10·SF-11 권고안 적용, 사용자 확인 대기)

| 파일 | 내용 |

적용 범위는 중단점 p1 이후 남은 WI(공통 잔여 + QMS-02~09)와 2026-11-06 작성한 PMS Vol.P1~P6(65건) + 공통 질문지 템플릿(CMN-00-QNR-001)이다. 이미 완료한 공통 WI(P0~P2, P3 일부)의 화면도 R1 검토 대상에 넣는다. PMS는 같은 방식(A → R → B)으로 진행하며, A단계 묶음 AP1·AP2를 A1 다음에 둔다(5.3절, 결정 SF-10).

## 2. 단계 구성

```
중단점 p1
  │
  ▼
[A단계] 1차 화면 개발(프로토타입)          ── 메뉴 순서, 묶음 A0 → A7
  A0 공통 잔여 화면 + 프로토타입 공용 장치
  A1 개발 품질 · 부품/협력사 품질(포털 포함)
  AP1 PMS 프로젝트·자원·일정·액티비티        ── 2026-11-06 추가(SF-10)
  AP2 PMS 비용·산출물·리스크·Gate·대시보드·AI·연계·성과 + 질문지 템플릿·대시보드 공용 라이브러리
  A2 제품/공정 품질
  A3 고객 품질
  A4 4M 변경 · 부적합
  A5 한도견본 · 교육 · 측정기 · MSA · 분석실
  A6 심사 · 인증 · 협력사 실적 · 개선 과제
  A7 대시보드 위젯 · AI 화면 · 연계 모니터
  │
  ▼
[R1] 1차 화면 검토·승인                    ── 개발 중단, 사용자 검토. 메뉴별 승인 기록
  │  (수정 라운드 최대 2회)
  ▼
[B단계] 상세 기능 개발                     ── 두 트랙 병렬: QMS P3 잔여 → P13, PMS P14 → P20. 승인된 메뉴부터
  각 페이즈 게이트(dev-plan 6.4) + 승인 화면 회귀 확인
  │
  ▼
[R2] 통합 검토(선택) → SIT 이관
```

- A단계 안에서는 묶음 순서를 지키되, 앞 묶음의 화면이 끝나면 다음 묶음으로 넘어간다(묶음 사이에 사용자 승인을 기다리지 않는다). 묶음마다 짧은 "화면 진행 메모"를 남겨 사용자가 원하면 중간에 미리 볼 수 있게 한다(승인 의미 없음).
- **R1에서는 개발을 멈추고 사용자 검토를 기다린다.** R1 승인 없이 B단계를 시작하지 않는다.
- B단계는 메뉴별 승인을 허용해, 승인된 메뉴의 WI부터 착수한다(결정 SF-5 권고). 선행 관계상 앞 페이즈 WI가 미승인 메뉴에 있으면 그 WI 승인을 기다린다.

## 3. "화면"의 정의 — A단계에서 만드는 것과 만들지 않는 것

### 3.1 A단계에서 만드는 것

| 구분 | 구성 요소 | 기준 |
| --- | --- | --- |
| 데이터 모델 | 명세 데이터 모델 표의 객체·필드·선택 목록 값·관계(Lookup·Master-Detail)·외부 키·레코드 유형 | 화면을 그리는 데 필요한 모델 **전체**를 명세 그대로 배포한다. 필드 API명은 B단계에서 바꾸지 않는 것을 전제로 한다 |
| 표준 화면 — 앱·내비게이션 | SL QMS·SL PMS 앱 탭 구성, 메뉴 순서, 모바일 내비게이션, 앱 페이지 탭 | 메뉴 번호 순서. 아직 화면이 없는 메뉴는 A0에서 자리(앱 페이지 "준비 중")를 먼저 둔다 |
| 표준 화면 — 레코드 | 페이지 레이아웃(섹션·필드 순서·필수 표시·관련 목록), 컴팩트 레이아웃(하이라이트·모바일 카드), Lightning 레코드 페이지(탭·컴포넌트 배치, 데스크톱·모바일 기본 보기 지정), 검색 레이아웃 | 명세 "화면/UX" 절. 레코드 페이지는 생성기 `recordPage` 키로 기본 보기 지정 |
| 표준 화면 — 목록 | 리스트 뷰(업무별 기본 보기·필터·열), 관련 목록 열 | 명세에 목록 요구가 없으면 "전체·내 것·진행 중" 3종 기본 |
| 표준 화면 — 상태 | 상태 진행바(`cmnStatusPath` + `CMN_StatusFlow__mdt` 레코드), 빠른 작업의 입력 화면 레이아웃 | 상태 값·순서는 명세 그대로. 전이 규칙은 B단계 |
| 커스텀 화면 | 명세의 모든 LWC(입력·판정·그리드 입력·조회·차트·위젯·모바일 화면), 화면 사이 이동, 로딩·빈 결과·오류·지연·잘림 상태 | 레이아웃·입력 요소·표시 형식 완성(4.2 충실도 표준) |
| 화면 컨트롤러 | 화면용 Apex 컨트롤러와 명세 DTO(조회 메서드는 실제 레코드를 읽음), 선택기(Selector) | 메서드 이름·DTO 필드는 명세 그대로 → B단계에서 그대로 씀 |
| 포털 화면 | Experience Cloud(LWR) 사이트·내비게이션 메뉴·페이지·포털 LWC, 포털 사용자 | 명세의 포털 화면 전부. 공유(협력사 격리)는 B단계 — A단계는 검토용 포털 사용자 1명으로 확인 |
| 문서 출력 화면 | Visualforce PDF·라벨(QR)의 레이아웃 | 레이아웃만. 라이브러리 결정(CR-8)이 필요한 부분은 자리표시 |
| 문구·권한 | Custom Label(ko·en_US·zh_CN), 탭·객체·필드 권한(PS·PSG), 검토용 열람 권한 | 번역은 초안으로 채우고 B단계 완료 전 검수(SF-4) |
| 데모 데이터 | 화면 검토용 데모 데이터 적재(전 객체) | 4.5절 |

### 3.2 A단계에서 만들지 않는 것(B단계)

- 업무 규칙(BR): 트리거 핸들러, 상태 전이 서비스, 계산·판정 로직, 필수값 외 검증 규칙, 중복·잠금 규칙.
- 공통 서비스 연결: 결재 유형 등록·콜백(`CMN_ApprovalCallback`), To-Do 생성·종료, 알림 규칙, 채번 규칙(`CMN_NumberingRule__mdt`) 연결, 공유 설정 등록(`CMN_SharingConfig__mdt`), 삭제 통제 규칙, 감사 이력 필드 지정.
- 메뉴 간 연결: 게이트웨이 바인딩(`QMS_GatewayFactory`), Platform Event 발행·구독.
- 연계: Snowflake 실조회(`CMN_DwQueryService`), Mule 수신 핸들러, SAP·MES 연계.
- AI: 프롬프트 템플릿, Agentforce 에이전트·액션, 추천 엔진.
- 배치·스케줄, Platform Cache, 성능 최적화, AC 시나리오 테스트(벌크 200건·권한 비교).

### 3.3 이미 구현된 공통 기능은 화면에서 실제로 쓴다

A단계 화면에서도 다음 공통 기능은 실제로 동작시킨다(이미 개발 완료): 결재선·상신·처리·이력·결재 현황(APV), To-Do, 코멘트 타임라인, 상태 진행바 표시, 문서·첨부 패널(DOC), 회의 패널(MTG), 코드 선택(cmnCodePicker), 사진 촬영·바코드(UX-001), 언어 전환. 단, 업무 객체의 결재 유형·콜백 등록은 B단계라, A단계에서 결재 컴포넌트는 "결재선 표시·편집"까지만 보이고 상신 버튼은 결재 유형이 등록되기 전까지 비활성 사유를 표시한다.

## 4. A단계 작업 방식

### 4.1 묶음 하나의 작업 순서

| 순서 | 작업 | 산출물 |
| --- | --- | --- |
| 1 | 화면 인벤토리 작성: 묶음 WI의 "화면/UX"·"데이터 모델"·"권한" 절을 읽고 화면 목록을 만든다 | `docs/docs/30-dev/screens/a{n}-{메뉴}.md` — 화면 ID(`{WI-ID}-S{nn}`), 유형(표준 레코드·목록·앱 페이지·커스텀·포털·모바일·PDF), 객체, 컴포넌트, 진입 경로, 페르소나, 모바일 여부, 프로토 한계 |
| 2 | 데이터 모델 정의 | `meta-src/{cmn,qms}/*.json`(객체·필드·선택 목록·관계·레이아웃·리스트 뷰·`recordPage`) → `python3 scripts/dev/metagen.py` |
| 3 | 표준 화면 | 생성기 산출물 + `flexipages/`(레코드·앱 페이지), 컴팩트 레이아웃, `CMN_StatusFlow__mdt` 레코드, 앱 탭 |
| 4 | 화면 컨트롤러·선택기 | `{접두어}_{도메인}Controller`(명세 메서드·DTO), `*Selector`(USER_MODE 조회). 업무 동작 메서드는 4.3 방식의 자리 구현 |
| 5 | 커스텀 LWC | 명세 컴포넌트 이름 그대로, Small 폼팩터, 라벨, 상태 표시(로딩·빈·오류·지연·잘림) |
| 6 | 권한 | 업무 PS(객체·필드·탭·클래스) → PSG, 검토용 열람 PS(4.7) |
| 7 | 점검·배포 | `scripts/dev/wi-check.sh <테스트 클래스>`(4.4 기준) → 개발 Org 배포 |
| 8 | 데모 데이터·화면 확인 | 데모 적재(4.5) → 페르소나별로 화면을 열어 인벤토리의 진입 경로대로 확인, 문제·한계를 인벤토리 "프로토 한계"에 적음 |
| 9 | 기록·커밋 | `screen-map.csv` 화면상태 `화면 완료`, 커밋 `[WI-ID] 화면: 요약`(WI 단위), 묶음 끝에 `[A{n}] {메뉴} 1차 화면 완료` 커밋과 화면 진행 메모 |

- 브랜치: 묶음마다 `ui/a{n}-{메뉴}`(예: `ui/a0-cmn`, `ui/a1-dvq-spp-iqc`). 묶음이 끝나면 다음 묶음 브랜치를 이전 묶음 브랜치에서 만든다. `main` 병합·push는 사용자 몫이다.
- DEV-STATUS의 WI 상태는 A단계에서 바꾸지 않는다(구현 진행은 B단계 기준). A단계 진행은 `screen-map.csv`의 `화면상태` 열(대기 → 화면 개발 중 → 화면 완료 → 검토 중 → 승인 / 재작업)로 관리한다.

### 4.2 화면 충실도 표준

| 요소 | A단계 수준 | B단계에서 바뀌는 것 |
| --- | --- | --- |
| 레이아웃·필드·배치 | 완성(명세 화면 절 그대로) | R1 변경분만 |
| 조회 데이터 | 실제 레코드(데모 데이터) | 공장·협력사 격리(공유)가 적용됨 |
| 저장(표준 레코드 편집) | 표준 저장 그대로(검증 규칙 없음) | 검증 규칙·트리거·채번이 붙음 |
| 업무 동작 버튼(판정·처분·발행·승인 요청 등) | 버튼·확인 대화상자·입력 폼까지 완성. 실행하면 "상세 기능 개발 단계에서 동작" 안내(라벨 `CMN_Prototype_NotYetAvailable`) | 서비스 구현으로 실제 동작 |

### 4.3 버리지 않는 프로토타입 원칙

A단계 코드는 B단계에서 그대로 이어 쓴다. 다시 만들지 않도록 다음을 지킨다.

1. 객체·필드·LWC·컨트롤러·DTO·라벨 이름은 명세와 `interfaces.md` 그대로 쓴다. 임시 이름(`*Proto`, `*Mock`)을 만들지 않는다.
2. 업무 동작 메서드는 서비스 시그니처(`QMS_{도메인}Service.{메서드}`)를 명세대로 만들고, 본문은 공용 자리 구현 `CMN_Prototype.notYetAvailable()`(A0에서 만듦: 라벨 문구의 `CMN_ValidationException`)만 호출한다. 화면 컨트롤러는 그 서비스를 부른다 → B단계는 서비스 본문만 채운다.
3. Snowflake 목은 업무 코드에 섞지 않는다(QMS-09-INT-003). `CMN_Prototype.mockResponse(queryKey, params)`가 정적 리소스 `CMN_PrototypeMocks`를 읽고, **기능 스위치 `CMN_PROTOTYPE_MODE`가 켜진 Org(개발·검토 Scratch)에서만** 동작한다. 운영·SIT에서는 스위치가 꺼져 있어 목이 응답하지 않는다(DEV-1 해소안, 결정 SF-2).
4. B단계 완료 조건: 메뉴의 `CMN_Prototype` 참조 0건(`scripts/ci/check-prototype-stubs.py`, A0에서 만듦 — WI 경로별 참조 수 출력). 모든 메뉴 B단계가 끝나면 `CMN_Prototype`·`CMN_PrototypeMocks`·검토용 권한을 삭제한다(삭제는 사용자 승인).
5. A단계 Apex도 테스트와 커버리지 85%를 지킨다(조회·DTO 변환·자리 구현 호출 테스트). 커버리지 미달 코드를 묶음 브랜치에 남기지 않는다.

## 7. B단계 — 상세 기능 개발

### 7.1 순서와 착수 조건

- 순서: 기반 P3 잔여 뒤에 두 업무 트랙을 병렬로 간다 — QMS P4 → … → P13, PMS P14 → … → P20([개발 플랜](dev-plan.md) 4.1절). 페이즈 안 레인·선행은 `phase-map.csv`와 페이즈 문서를 쓴다.
- 한 사람(에이전트)이 두 트랙을 같이 할 때의 우선순위: (1) 기반 P3 잔여(QNR-001·대시보드 공용 라이브러리 포함), (2) PMS 1차 오픈 범위가 끌고 오는 QMS WI 14건(dev-plan 4.4절), (3) PMS 1차 오픈 범위(P14~P18의 W1), (4) QMS W1, (5) 나머지 W2·W3. PMS 오픈(2027-10)이 QMS(2027-4Q)보다 이르기 때문이다.
- WI 착수 조건: (1) 그 WI 메뉴의 R1 승인, (2) 명세 승인 또는 검토 전 명세 동의, (3) 선행 WI `개발 완료`.
- 화면이 없는 WI(연계 API·배치·Snowflake·AI 엔진 등, `screen-map.csv` "B단계만" 50건)는 R1과 무관하게 선행만 맞으면 착수할 수 있다. 단, R1 기간에는 개발을 멈추므로 R1 승인 후 시작한다.

### 7.2 WI 하나의 B단계 작업

1. A단계 산출물(화면·컨트롤러·서비스 자리 구현)과 R1 피드백·변경 요청을 확인한다.
2. 업무 규칙: 서비스 본문(`CMN_Prototype` 호출 제거), 트리거 핸들러, 검증 규칙, 상태 전이, 계산·판정.
3. 공통 서비스 연결: 결재 유형·콜백, To-Do, 알림 규칙, 채번, 공유 설정(공장·협력사 격리), 삭제 통제, 감사 이력.
4. 메뉴 간 연결: 게이트웨이 바인딩, Platform Event.
5. 연계·AI: Snowflake 실조회(목 → L1 테스트 → L3), Mule 수신, AI 서비스.
6. AC별 테스트(벌크 200건, 음수, 권한 비교), 커버리지 85%, Jest 동작 테스트 보강.
7. `/implement-wi` 흐름대로 점검·배포·보고서(`docs/wi/{WI-ID}.md` — A단계 화면 작업 내역도 함께 기록)·DEV-STATUS·커밋.

### 7.3 게이트

- 페이즈 게이트(개발 플랜 6.4)를 그대로 하고, 추가로 **승인 화면 회귀**(R1 판정 화면과 달라진 곳이 없는지, R2 항목 제외)를 확인한다.
- 메뉴의 B단계가 모두 끝나면 `check-prototype-stubs.py`로 그 메뉴 참조 0건, 검토용 PS에서 그 메뉴 객체 제거.

### 7.4 R2(선택) — 통합 검토

B단계 전체 완료 후(또는 PoC 시나리오 단위로) 화면 + 기능 통합 검토를 한다. R1 이후 모은 화면 변경 요청을 여기서 반영한다. 끝나면 `CMN_Prototype` 관련 메타데이터 삭제(사용자 승인)와 SIT 이관 준비(P13).

| A단계 중 공통 WI 기능 부족 발견 | 화면 확인 막힘 | 공통 WI 변경 요청으로 기록하고 B단계 P3 잔여에서 처리. 화면 확인에 꼭 필요하면 A0 보완으로 처리하고 보고 |

## 11. 진행 관리

- **A단계**: `screen-map.csv` 화면상태 열, 묶음 인벤토리, 화면 진행 메모(묶음 완료 커밋 메시지 본문). DEV-STATUS는 바꾸지 않는다.
- **R1**: `screen-review-pack.md`의 메뉴별 판정·피드백.
- **B단계**: 기존대로 DEV-STATUS(WI 상태)와 페이즈 문서 게이트 기록.
- **플랜 변경**: 묶음 배정은 `screen-map.csv`, 상세 페이즈 배정은 `phase-map.csv`를 고친다. 상세 페이즈를 바꿨으면 `cd docs && python3 scripts/build_dev_plan.py`로 선행 위반을 검사한다.
- **에이전트 작업 원칙**: A단계 안과 B단계 안에서는 권고안으로 스스로 결정하며 멈추지 않고 진행한다. **R1에서는 반드시 멈추고 사용자 검토를 요청한다.**
